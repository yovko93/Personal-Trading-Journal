# Trading Calendar

## M13.1 — Read-only monthly data

`TradingCalendarQuery(year, month, tradingAccountId?)` selects a displayed New York calendar month. `null` Account means all accounts; an empty Account ID is invalid. `ITradingCalendarReader.GetAsync` returns `TradingCalendarMonth` with `MonthStart`, `GridStart`, `GridEnd`, the complete ordered `GridDates`, and one `TradingCalendarCurrency` per historical pricing currency with matching Trades. The grid begins on Monday on/before the first of the month and ends on Sunday on/after the last. It has four to six complete rows. For example, September 2026 includes August 31 through October 4. Adjacent-month days are marked by `IsInDisplayedMonth` but contribute normally to their visible week's totals. Even an empty month has a complete date grid and no fabricated currency bucket.

The reader delegates **one** inclusive grid-date query to `IDashboardAnalyticsReader`, which filters fully closed Trades by `ClosedAtUtc` using the existing DST-safe New York midnight boundaries. Open and partially exited Trades do not contribute. It does not use Trades-list paging, current Instrument pricing, source import TradeDay, or a retained snapshot. The underlying fresh-context query is no-tracking and projects authoritative persisted Gross, Net, and historical currency, not displayed prices or executions. No database writes are made; cancellation is forwarded to the SQL query and checked during shaping. An Account filter applies to every date and weekly summary. An unavailable Account ID yields an empty result, not another Account's Trades.

Each currency has ordered `TradingCalendarWeek` rows, each with seven `TradingCalendarDay` values and a Monday–Sunday `ClosedTradeMetrics` summary. Weekly totals and closed-Trade counts include **Sunday**, although the later UI places the summary in that row's **Saturday cell**. Day and week metrics directly reuse M12's `DashboardMetricCalculator` output. There is no cross-currency monetary total. `Metrics == null` means **no closed Trades** for a day or week; `ClosedTradeCount == 0` is its convenience count, not a financial zero. A populated period with `EffectiveNet.Total == 0` is a genuine zero. `EffectiveNet.Total == null` for a populated period means complete numeric P&L is unavailable; `KnownSubtotal` and `Coverage` remain explicit partial evidence, not a total.

Effective Net uses authoritative Net when costs are known. For a closed Trade with unknown costs and known Gross, it uses Gross as an **estimate** without changing stored cost or Net nullability. `IsEstimated` and `EstimatedTradeCount` retain that provenance at both day and week scope. Unknown Gross cannot become a numeric estimate. Strict verified `Net` and its coverage remain available separately. All amounts retain full decimal precision; display rounding is a future UI concern.

## M13.2–M13.3 UI reference

The supplied screenshot is a visual reference, **not an implemented screen**. The future Calendar should have a Monday–Sunday month grid with adjacent-month dates visible, daily P&L sign coloring and closed-Trade counts, and one Monday–Sunday weekly P&L/count summary shown in each row's Saturday cell. Sunday activity must already be included in that summary. The UI must label the selected currency and avoid visually summing currencies. It must distinguish no-Trades, genuine zero, estimated, and unavailable results, and keep Account selection and month navigation consistent with the read-only query. The screenshot's colors, spacing, and controls are guidance for later presentation work, not a new P&L definition.
